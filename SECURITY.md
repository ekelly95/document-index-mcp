# Security

## Reporting a vulnerability

Open a [private security advisory][advisory]. Do not open a public issue for a
suspected vulnerability.

[advisory]: https://github.com/ekelly95/document-index-mcp/security/advisories/new

This project has no bug bounty. The maintainer aims to reply within two weeks.

## Security model

This is a local MCP server that talks over stdio. It has no network listener, no
account, no hosted API, no database server, and no application secret. It reads
files beneath one directory the user chooses, and writes one SQLite index inside
it.

It makes exactly two kinds of outbound request, both one-time downloads of its
own machinery. Neither carries any part of a user's documents, and no document
content leaves the machine except to the MCP client the user connected:

- the embedding model, ~130 MB from
  `storage.googleapis.com/qdrant-fastembed`, on first ingest;
- OCR language data, ~3 MB per language from `cdn.jsdelivr.net`, on the first
  scanned PDF only. `--ocr-lang-path` points this at a local directory instead
  and removes the request.

Three supply-chain facts, stated here rather than left to be discovered:

- **Neither download is integrity-checked** — no checksum, no signature, on
  either the model or the language data. A compromised bucket or a broken TLS
  path would be trusted. This is recorded in `docs/roadmap.md` and is the honest
  limit of both pipelines.
- **The model archive is unpacked by `tar`, and that dependency is pinned
  deliberately.** `fastembed` asks for a `tar` 6 line that is end-of-life with a
  critical advisory against it, so `pnpm-workspace.yaml` overrides it to `tar` 7
  and patches the one import that would otherwise break. Since that pin is the
  thing standing between an unverified download and an extractor with a
  known arbitrary-file-write hole, it is no longer left to the lockfile alone:
  CI asks the resolver what `fastembed` actually loads and fails the build on a
  `tar` 6, because a lockfile regenerated by a tool that does not read
  `pnpm-workspace.yaml` would otherwise put one back with every job green.
- **No installable archive is published.** The release is a tag and its
  changelog entry, nothing more. `pnpm pack` still runs in CI, as a test that
  the `files` allowlist is right and that the package starts outside the
  development checkout — but the artifact is not attached, because `npm
  install`ing it resolves `fastembed`'s own dependency range and gets the
  unpatched `tar`, and none of the protection above travels with it.
  Distribution is by cloning.

One thing that looks like a finding and is not: a `node_modules/.pnpm/tar@6.2.1`
directory survives in a development checkout that predates the override, hanging
off an orphaned copy of the unpatched `fastembed`. Nothing references it — the
lockfile resolves a single `tar` 7 — but a scanner that walks the filesystem
rather than the dependency graph will report it. A fresh install clears it.

The documents are untrusted. A PDF, a Word file or a Markdown note may have come
from anywhere, and the parsers are the attack surface. The server therefore:

- treats the library root as a jail. Containment is checked with
  `path.relative`, never `resolved.startsWith(base)` — a sibling directory named
  `library-secrets` shares the `library` prefix and would pass the `startsWith`
  form while sitting outside the root;
- refuses symlinks that pass the lexical check but physically escape, and uses
  the canonical real path afterwards so one file cannot enter the index under
  two names;
- gates on an extension allowlist, so that pointing the server at a directory
  which also happens to hold `.env` or `id_rsa` does not make those addressable
  at all — the allowlist is a guard, not the format decision, which is made from
  magic bytes downstream;
- reads `.docx` archive entries by fixed name, into memory, never onto disk,
  and bounds what one archive can make it inflate **twice over**: 20 MB for any
  single entry, and 80 MB across the archive as a whole. Both are needed. A zip
  may repeat an entry name as often as it likes, so a per-entry cap alone let
  thousands of records all pass the four-name test and all be inflated — a
  3.7 MB file measured 4.0 GB of inflation and 8.9 seconds of a server that
  answers nothing, since the unzip is synchronous. A repeated name is now
  skipped rather than counted, and the total is a hard stop;
- refuses a file larger than 512 MB before reading it, `--max-file-mb` to
  change. The document is read whole into memory and text formats are then
  decoded into a string on top of that, so without a ceiling the only limit was
  Node's own — which is a crash rather than a refusal;
- reads only a Word document's `w:t` runs, so tracked deletions, comments,
  headers and footers cannot reach the index and cannot be searched out of it;
- never lets query text become query syntax: search terms are extracted and
  quoted individually before reaching FTS5, and every SQL statement is
  parameterised;
- returns no document bodies from search. The output schema for a search hit has
  no text field, so a refactor cannot quietly regress it. `get_chunk_context` is
  the only tool that returns body text, hard-capped at 24,000 characters;
- exposes library-relative paths, never absolute ones — including in failures.
  Every error returned to the caller is scrubbed of the library root, the index
  path and the model cache on the way out, rather than only the four filesystem
  errors that had a hand-written message. An allowlist of error codes is always
  one code short: a symlink loop inside the library raises `ELOOP`, which no
  such list contained, and Node's text for it carries the absolute path.

Two limits of that model, stated rather than left implicit:

- **The real-path check does not close a race.** A hostile local user could
  replace a file with a symlink between the check and the read. That requires an
  account on the machine, which is already outside this model, but the guard is
  not atomic and should not be described as though it were.
- **The allowlist stops secrets being addressable; it does not stop a private
  notes tree inside the root being addressable.** Choose a library root wide
  enough to hold your documents and no wider.

## The conversion script

`scripts/convert-for-ingest.ps1` is the one part of this project that hands an
untrusted document to a program which will run what is inside it. It drives the
installed Word and PowerPoint through COM to turn `.doc` and `.ppt` into formats
the server reads, and opening a legacy Office file is exactly what `AutoOpen`
and `AutoExec` macros are for.

The default it used to inherit was the worst of the three available. An Office
application started through Automation begins at `msoAutomationSecurityLow` —
measured as `1` on a real install rather than assumed — which runs every macro
without prompting, so the script was a *weaker* way to open an untrusted file
than double-clicking it would have been.

It therefore sets `AutomationSecurity` to force-disable before opening anything,
so macros never run whatever the machine's Trust Center says; turns off
`UpdateLinksAtOpen`, so a linked or DDE field cannot reach out the moment a file
opens; and disables alerts, because a password prompt on an invisible
application is a dialog nobody can answer.

The script is run by hand, never by the server, and it is not covered by CI —
there is no runner with Office on it. It is verified against real files by hand
before release.

Please report any bypass of these controls, any way to read or write outside the
chosen root, and any input that causes code execution or unbounded resource use.

## Out of scope

- Vulnerabilities in `pdfjs-dist`, `tesseract.js`, `better-sqlite3`,
  `sqlite-vec` or `fastembed`, which should be reported to those projects.
- Retrieval quality. The fusion score orders results without measuring
  relevance, so a search of a library that does not cover the question still
  returns a confident-looking five. That is a known defect, recorded in
  `docs/roadmap.md`, not a vulnerability.
- OCR errors, and text a parser cannot recover from a malformed file.
- Anything the MCP client does with what this server hands it. Passage text is
  document content and should be treated as untrusted by whatever reads it.
- Attacks that require prior control of the machine, the library root, or the
  files being indexed.

## Supported versions

Only the latest release is supported.
